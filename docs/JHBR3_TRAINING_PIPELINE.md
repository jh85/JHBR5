# JHBR3 training pipeline

This memo describes the supervised-learning pipeline currently used for
JHBR3:

```text
PACK/PSV records
    -> aggregated NPZ shards
    -> PyTorch checkpoints
    -> dynamic ONNX
    -> mixed-precision ONNX
    -> TensorRT engine
```

The trained network uses:

- 148 input planes
- 2,187 policy outputs
- a WDL value head
- a moves-left (MLH) head

JHBR3 retains the inherited `jhbr2` model-format name for compatibility.

## 1. Prepare the training records

Collect strong shogi records in one or both of these formats:

- **PACK:** Complete game records. These provide positions, played moves,
  evaluations, game results, and exact remaining plies for MLH.
- **PSV (`.bin`):** Teacher-position records. These provide positions, moves,
  evaluations, and game-result labels, but normally do not contain the true
  game ending. The MLH label is therefore masked by default.

Input quality matters. Prefer games or teacher positions generated by strong
engines with sufficiently deep searches. Mixing multiple sources is allowed,
but a much larger corpus will naturally contribute more raw observations to
the aggregated targets.

## 2. Build the optional packed-plane encoder

Packed shards are strongly recommended for large training sets:

```bash
cd /workspace/JHBR3
bash pyext/build.sh
```

The packed format greatly reduces shard storage and per-DDP-process RAM. The
trainer automatically detects and unpacks it.

Without `--packed`, one 500,000-position shard expands to roughly 12 GB of
float16 planes when loaded by each DDP process. If packed generation is not
available, use a smaller `--shard-size`, such as 100,000.

## 3. Convert PACK and PSV into aggregated shards

```bash
cd /workspace/JHBR3

python3 gen_agg_shards.py \
  --pack-dir /path/to/packs \
  --psv-dir /path/to/bins \
  --output-dir /workspace/agg_shards \
  --shard-size 500000 \
  --workers 32 \
  --partitions 512 \
  --policy-method temperature \
  --alpha 0.5 \
  --packed \
  --stats-json /workspace/agg_shards/stats.json
```

Either `--pack-dir` or `--psv-dir` can be omitted when only one input format
is available.

The converter groups identical positions by their canonical
HuffmanCodedPos. Each unique position becomes one training sample containing:

- A sparse distribution over all observed moves.
- A WDL target blending evaluation-derived win probability and recorded game
  results.
- Mean remaining plies where a valid MLH label exists.
- The number of raw observations that contributed to the sample.

With:

```text
--policy-method temperature --alpha 0.5
```

the policy weight of each move is proportional to:

```text
sqrt(number of observations of that move)
```

This preserves move-frequency information while reducing the dominance of
the most frequently recorded move.

### Partition count

`--partitions` controls conversion resource usage, not the meaning of the
training targets:

- More partitions reduce phase-two RAM per partition but create more
  temporary files and overhead.
- Fewer partitions reduce file overhead but require more RAM per worker.
- The default is 256.
- 512 is a reasonable choice for a large corpus.
- Billions of raw records may require several thousand partitions.

Approximate phase-two record memory per partition is:

```text
raw_record_count * 40 bytes / partition_count
```

### PSV moves-left labels

The default is:

```text
--psv-mlh none
```

This writes `-1` for PSV MLH targets, causing the trainer to mask their MLH
loss. `--psv-mlh recorded-end` estimates moves-left using the last recorded
position, but that is not necessarily the true game ending.

### Output

The files are named:

```text
/workspace/agg_shards/aggshard_*.npz
```

The trainer must receive the filename prefix, not merely the directory:

```text
/workspace/agg_shards/aggshard
```

Inspect `/workspace/agg_shards/stats.json` after generation. It records raw
and unique position counts, duplicate rates, result conflicts, move
distributions, and MLH coverage.

## 4. Train the neural network

Example for eight GPUs:

```bash
cd /workspace/JHBR3

torchrun --nproc_per_node=8 shogi_train.py \
  --data /workspace/agg_shards/aggshard \
  --epochs 3 \
  --lr 3e-4 \
  --warmup-steps 4000 \
  --grad-clip 0.5 \
  --bf16 \
  --pre-norm \
  --gated-attention \
  --d-model 1024 \
  --encoders 20 \
  --heads 16 \
  --batch 128 \
  --grad-accum 1 \
  --workers 12 \
  --save-dir /workspace/checkpoints \
  --save-every 1 \
  --log-csv run.csv \
  --log-file run.log
```

This configuration means:

- One DDP process per GPU.
- Micro-batch size 128 per GPU.
- Gradient accumulation of 1.
- Global batch size `128 * 8 * 1 = 1,024`.
- BF16 autocast without an FP16 gradient scaler.
- Pre-normalized transformer residual blocks.
- Gated attention.
- Model width 1,024, 20 encoder blocks, and 16 attention heads.
- Linear learning-rate warmup followed by per-step cosine decay.
- Gradient norm clipping at 0.5.

`--workers 12` is per DDP process, so eight ranks may create as many as 96
DataLoader workers. Reduce it if CPU utilization, RAM pressure, or process
contention becomes excessive.

`--compile` can optionally improve training throughput, but the first batches
are slower while compilation occurs. It can be omitted when stability and
simple debugging are more important.

### Checkpoints

With `--save-every 1`, rank zero writes:

```text
/workspace/checkpoints/shogi_bt4_epoch1.pt
/workspace/checkpoints/shogi_bt4_epoch2.pt
/workspace/checkpoints/shogi_bt4_epoch3.pt
```

Monitor all loss heads:

- `policy`
- `value`
- `mlh`

Three epochs is a valid run configuration, but it is not guaranteed to be the
optimal stopping point. Playing-strength tests remain the final criterion.

### Resume training

`--epochs` is the final total epoch number, not the number of additional
epochs. To resume epoch 3 and train through epoch 6:

```bash
torchrun --nproc_per_node=8 shogi_train.py \
  --data /workspace/agg_shards/aggshard \
  --resume /workspace/checkpoints/shogi_bt4_epoch3.pt \
  --epochs 6 \
  ...other original options...
```

Keep the architecture options identical to the original run.

### Fine-tune epoch 3 for independent promotion scoring

The policy head now has a zero-initialized `promotion_delta` layer. It adds a
contextual logit correction to the ten promotion directions without changing
the 2,187-output model interface:

```text
non-promotion logit = existing attention move logit
promotion logit     = existing attention move logit + promotion_delta
```

An older epoch-3 checkpoint does not contain the two new tensors. Use
`--finetune-from`, not `--resume`: the former permits exactly this migration,
keeps every existing weight, leaves the new layer at zero, and starts a fresh
optimizer/LR schedule. `--resume` remains strict and is only for an exact
current-format continuation.

Fine-tuning stages that freeze different parameters must be separate
invocations. DDP registers trainable parameters when it starts and cannot
safely unfreeze a previously omitted parameter set in-place.

#### Two-GPU stage 1: promotion branch only

This example processes about 3.1 million positions
(`12,000 steps × global batch 256`):

```bash
cd /data/new_jhbr2/JHBR3
mkdir -p promotion-finetune/stage1

/data/new_jhbr2/venv/bin/torchrun --nproc_per_node=2 shogi_train.py \
  --data /data/new_jhbr2/shards2/aggshard \
  --finetune-from /data/new_jhbr2/shogi_bt4_epoch3.pt \
  --finetune-scope promotion \
  --epochs 1 \
  --lr 3e-4 \
  --promotion-lr 3e-4 \
  --warmup-steps 500 \
  --grad-clip 0.5 \
  --bf16 \
  --batch 128 \
  --grad-accum 1 \
  --workers 6 \
  --max-steps 12000 \
  --save-dir promotion-finetune/stage1 \
  --save-every 1 \
  --log-csv promotion-finetune/stage1/run.csv \
  --log-file promotion-finetune/stage1/run.log
```

The transformer is frozen, so activation checkpointing is unnecessary. The
step-limited run writes `shogi_bt4_step12000.pt`. A partial-epoch checkpoint
has no saved data cursor and deliberately cannot be passed to `--resume`; it
is the initialization for the next `--finetune-from` stage.

#### Two-GPU stage 2: heads plus the last four encoders

Start conservatively with about one quarter of a corpus pass:

```bash
mkdir -p promotion-finetune/stage2

/data/new_jhbr2/venv/bin/torchrun --nproc_per_node=2 shogi_train.py \
  --data /data/new_jhbr2/shards2/aggshard \
  --finetune-from promotion-finetune/stage1/shogi_bt4_step12000.pt \
  --finetune-scope last \
  --finetune-last-encoders 4 \
  --epochs 1 \
  --lr 1e-5 \
  --trunk-lr 1e-5 \
  --policy-lr 1e-4 \
  --promotion-lr 1e-4 \
  --warmup-steps 1000 \
  --grad-clip 0.5 \
  --bf16 \
  --grad-checkpoint \
  --batch 32 \
  --grad-accum 4 \
  --workers 6 \
  --max-steps 100000 \
  --save-dir promotion-finetune/stage2 \
  --save-every 1 \
  --log-csv promotion-finetune/stage2/run.csv \
  --log-file promotion-finetune/stage2/run.log
```

Here the effective global batch remains
`32 × 2 GPUs × 4 accumulation = 256`. Reduce the micro-batch and increase
accumulation by the same factor if a 24 GB GPU runs out of memory.

Evaluate stage 2 before unfreezing the complete trunk. A later full-model
stage uses `--finetune-scope full` and can retain the same differential
learning rates. Always use a new output directory so the original epoch-3
checkpoint remains untouched.

## 5. Convert a checkpoint to ONNX

`checkpoint2onnx.py` does not create a TensorRT engine directly. It creates
two ONNX files:

1. A dynamic FP32 ONNX model.
2. A dynamic mixed-precision ONNX model intended for TensorRT 11.

```bash
cd /workspace/JHBR3

python3 checkpoint2onnx.py \
  /workspace/checkpoints/shogi_bt4_epoch3.pt \
  1 \
  --dynamic
```

Output:

```text
shogi_bt4_epoch3_dynamic.onnx
shogi_bt4_epoch3_dynamic_fp16.onnx
```

The positional `1` is the dummy export batch. `--dynamic` makes the batch
dimension dynamic so TensorRT can build a runtime profile supporting multiple
batch sizes.

The exporter restores the architecture configuration stored in the
checkpoint. It also uses ModelOpt to retain numerically sensitive operations
in FP32 while converting suitable operations to FP16.

## 6. Convert ONNX to a TensorRT engine

For an engine intended for `MinibatchSize=256`:

```bash
cd /workspace/JHBR3
mkdir -p engines

$TENSORRT_PATH/bin/trtexec \
  --onnx=shogi_bt4_epoch3_dynamic_fp16.onnx \
  --saveEngine=engines/shogi_bt4_epoch3_trt_o256_m256_ws16384.engine \
  --minShapes=input_planes:1x148x9x9 \
  --optShapes=input_planes:256x148x9x9 \
  --maxShapes=input_planes:256x148x9x9 \
  --memPoolSize=workspace:16384M
```

For TensorRT 11, do not add `--fp16` to this command. Mixed precision has
already been encoded into `shogi_bt4_epoch3_dynamic_fp16.onnx`.

The TensorRT maximum profile batch must be at least as large as the intended
JHBR3 minibatch. Requests above the engine's maximum profile are split and do
not produce a true larger inference batch.

TensorRT engines are tied to the deployment environment. Rebuild them when
the GPU architecture, TensorRT version, CUDA stack, or relevant runtime
compatibility changes.

## 7. Configure JHBR3

In the USI configuration:

```text
setoption name OnnxModel value /workspace/JHBR3/engines/shogi_bt4_epoch3_trt_o256_m256_ws16384.engine
setoption name ModelFormat value auto
setoption name MinibatchSize value 256
```

The `jhbr2` model-format value remains available because JHBR3 intentionally
preserves compatibility with the inherited 148-plane model interface.

## 8. Validate the new network

Before adopting a checkpoint:

1. Confirm that TensorRT loads the engine and reports 148 input channels.
2. Run a short USI smoke test and verify that legal moves and normal `info`
   lines are produced.
3. Run paired strength tests against the previous engine using identical
   openings, hardware topology, node/time control, and engine options.
4. Extend the match until the confidence interval is useful.
5. Retain the previous checkpoint, ONNX, TensorRT engine, commands, logs, and
   strength-test results so the experiment is reproducible.

Network loss is useful for detecting training problems, but lower loss alone
does not prove greater playing strength.
